# 业务事务与Redis方案

本文是后续Spring Boot服务实现的约束说明。数据库已提供字段、索引及行级约束；以下工作流尚未实现，不把数据库结构等同于完整售票系统。

## 影院隔离与权限

请求通过登录用户查询有效的sys_user_role，结合sys_role_permission判定操作码。影院角色必须具备目标cinema_id的授权；禁止相信前端传入的影院ID。查询订单、场次、会员、评价和反馈时强制加影院条件，写操作在事务中再次校验对象所属影院。跨影院管理员即使猜到资源主键也应返回拒绝或不存在。

普通用户只能读写自己的订单、锁座、电子票、优惠券与反馈。平台接口有独立权限码；影院角色不得被动态授予platform前缀权限。授权变更后失效用户权限缓存，并写sys_audit_log。资质文件通过受权限保护的存储键读取。

影院入驻：先创建PENDING影院，再提交cinema_application。系统管理员审核通过时，在同一事务中更新申请、激活影院并写审计。影院管理员申请独立走cinema_admin_application；审批通过后插入带cinema_id的授权记录。不允许申请人自审，不允许在影院未获准入驻时开售。

## 排片、布局和票价

新建或修改排片前，先SELECT影院影厅行FOR UPDATE，以该影厅作为串行化资源，再检查现有非取消场次是否与新区间重叠。冲突条件为existing.starts_at < new.hall_release_at且existing.hall_release_at > new.starts_at。结束时间之外还包含清场时间；不能仅给(hall_id,starts_at)加唯一索引就声称避免时间重叠。校验影片在本院片库启用、平台已发布、片长与清场时间合理。

发布场次时，按cinema_seat生成screening_seat快照；可视化座位图使用库存的坐标和名称，不能用另一场次的库存。存在已开售或已售场次的布局不可原地改行列或复用座位ID，须停用旧布局、保留引用，再按新布局建立后续场次。售票后不得直接改开场时间、物理影厅和影片；通过撤场退款等显式流程处理。

票价规则按生效日期、星期掩码、场次时段、影厅和影片过滤，priority降序、id升序确定唯一规则。生成场次基础价，再叠加物理座位surcharge形成库存价。跨午夜的时段规则拆成两条。已有锁座、订单和出票使用快照价格，后续调价不能改历史账。

## 锁座与订单

推荐初始锁座时长10分钟，前端展示服务端expires_at，不信任客户端倒计时。用户下单与支付不能重置这10分钟。

1. 去重并排序用户选择的库存ID，限制单次张数，检查是否属于同一场次、仍在售票窗口且影院营业。
2. Redis可先对场次使用短时协调锁booking:screening:{screeningId}，减少数据库竞争。每次锁使用高强度随机持有者令牌并带TTL。Redis失败时可降级到MySQL事务或返回繁忙，不能跳过数据库判断。
3. MySQL事务中建立seat_hold，按库存ID升序SELECT FOR UPDATE检查所有目标行。如果库存被占用，只有在确认旧批次已过期、旧订单未支付，并完成旧单取消与明细释放后才可回收，不能用简单时间判断抢走正在结算的座位。
4. 将全部目标库存从AVAILABLE改为LOCKED，填active_hold_id和locked_until，同时增加version；影响行数必须等于请求张数，否则整批回滚。插入seat_hold_item保存锁座与票价快照。
5. 成功提交后返回hold_no、仅给持有人使用的原始凭证和截止时间，数据库只保存摘要。提交事务时一并写Outbox，通知缓存失效或WebSocket座位状态推送；移动端仍以服务端重新查询为准。
6. 创建订单时锁定批次与全部库存，检查持有人、凭证摘要、批次状态、到期和每个库存的active_hold_id。一个hold_id只生成一个订单；凭证不能从其他用户转用。
7. 按“库存原价→会员折扣→优惠券”计算，先四舍五入会员价到分，再计算券优惠到分，抵扣不超过剩余票款。一单最多一张券，满减门槛按原价合计核验；校验券所属人、影院范围、有效期与状态。
8. 插入ticket_order和ticket_order_item，锁定优惠券并写coupon_usage；hold置ORDERED。支付截止取锁座截止与场次停售时间的较早值。零元订单直接通过独立零元结算分支原子出票，settled_payment_id保持NULL，不伪造正额渠道支付。

关键库存更新示意（命名参数由后端绑定，整批操作必须在事务中）：

```sql
UPDATE screening_seat
SET status = 'LOCKED', active_hold_id = :holdId,
    locked_until = :expiresAt, version = version + 1
WHERE id = :inventoryId AND screening_id = :screeningId
  AND cinema_id = :cinemaId AND status = 'AVAILABLE';
```

普通读之后再无条件写不能防止并发抢座。InnoDB锁定读与事务行为参见[MySQL官方文档](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)。同一场次同一座位唯一键、有效订单明细库存唯一键、带条件写入及事务共同保护库存。

## 支付回调与超时释放

支付创建先写payment_transaction，再调用渠道，使用payment_no和idempotency_key应对重试。渠道网络调用不得在持有数据库行锁时长时间等待。MOCK仅用于开发演示，真实支付回调必须验签、校验商户和应用标识、币种、订单及金额。

验签后的回调先按(provider,provider_event_id)唯一键写payment_callback_event。重复事件读取原处理结果；处理失败可重试，不能因“已经收过事件”而忽略尚未完成的业务。缺少可靠事件ID的渠道由适配器基于渠道业务号与事件类型生成稳定幂等标识。

支付成功处理与取消、超时释放共用订单行锁。保持一致资源顺序：先订单，再锁座批次，再按ID升序库存及明细，再电子票、优惠券和会员账户。仅锁座阶段还没有订单，从锁座批次开始。所有入口遵循同一顺序；遇死锁只做有限重试，重试仍使用原幂等键。

未到期且库存仍属于本批次的UNPAID订单，金额核对后原子更新支付SUCCESS、认领settled_payment_id、更新订单PAID、明细VALID、库存SOLD并指向明细、清空锁座字段、批次CONSUMED、券USED和生成电子票，最后记录积分、状态历史与Outbox。ticket.order_item_id唯一保证不重复出票；积分发放有独立幂等键。

若订单已经关闭、已到期或座位已被释放，即使渠道扣款成功也不得抢回座位。保留真实成功支付流水，创建LATE_PAYMENT退款。不同渠道尝试发生第二笔真实扣款时，同样记录SUCCESS，创建DUPLICATE_PAYMENT退款；订单只认领一笔，额外扣款不计票房，不能用订单唯一成功支付约束掩盖真实资金流。

定时释放任务按索引扫描过期hold与UNPAID订单，逐单加锁后二次判定。将原订单置EXPIRED、明细CANCELLED、可用券释放，再只释放active_hold_id仍指向原批次的LOCKED库存，清空锁字段。若支付事务已先完成，跳过释放。无订单的HELD批次也要回收。Redis过期通知只作提醒；周期补扫必须存在，以覆盖进程重启和丢消息。

## 退票与改签

用户按订单明细发起，可选一张或多张未核销且未超截止时间的票。锁订单、明细及电子票，按购票快照规则算手续费和可退金额。after_sale_item的有效占用唯一键阻止同票并发退改；申请时票置FROZEN、递增qr_version，库存仍为SOLD，不先释放座位。拒绝或用户取消时恢复原票VALID，解除占用并记录审核。

审核通过后通过Outbox提交退款，payment_refund用唯一退款号和幂等键。退款前锁原支付行，计算已成功退款和未终结占用退款的总额，禁止超过该支付实付。异步回调验签后只推进一次；失败保留可重试记录，不把“请求已发送”当作“退款已成功”。

退票完成事务更新退款SUCCESS、订单与逐票成功退款额，原票REFUNDED、明细REFUNDED，核实库存当前仍由该明细拥有后才释放。明细不允许在核销后退款。订单主状态与退款维度分开：PAID订单可以部分或全部退款，通过金额及逐票状态展示“部分退款/全部退款”，不强行丢失原支付事实。

改签限制同一影院、未核销票，目标可以是同影片其他场次；若允许跨影片，服务端必须明确规则，默认本课题只允许同影片同院改签。目标票先按普通锁座形成新订单，申请关联target_screening_id与new_order_id，原票保留并冻结。新旧票按同样张数逐票映射，校验目标券及优惠使用规则，券不自动复用到新订单。

新票应收为目标票价及优惠后的完整金额。为避免把“只付差价”误记成新订单全额实收，当前数据模型采用**原票退款+新单全额支付**的可追溯资金路径；price_difference仅用于界面展示新旧净支出差额。差价为正显示补差，为负显示退差，但支付页须明确展示实际全额收款与原单退款两笔。若要钱包余额抵扣式直接补差，需要另加资金账户与余额流水，当前不假定存在。

审批通过后先完成新单支付与出票，再推进原票退款；在新票成功、原退款成功之前不得标记改签COMPLETED。新支付失败或超时，取消新单并解冻旧票；新票已成功但原退款失败时，申请维持PROCESSING、冻结原票并重试退款，保留人工处理入口。原票退款成功后置EXCHANGED并释放原座位，原新票关系写入after_sale_item。不得以覆盖旧订单的场次与座位来实现改签。

## 动态二维码与核销

用户请求二维码时校验票归属与VALID状态，用加密安全随机源签发nonce并保存摘要；原始nonce只在HTTPS返回。建议有效期30秒，带ticket_no、qr_version、nonce和expires_at及服务端签名。密钥从环境或密钥配置读取，不进数据库或仓库。刷新二维码不必撤销仍在30秒窗口内的前一码，但所有凭证共享票状态与版本，成功核销或退改即可整体失效。

验票员必须拥有扫码影院的cinema:ticket:verify权限。先验签和有效期，再通过票据查订单ID，在事务中遵循订单→明细→票的统一锁顺序，并验证影院、场次验票窗口、nonce未消费、版本与票状态。成功时以条件更新将票置VERIFIED、明细VERIFIED、token记录consumed_at，写一条SUCCESS核销日志；数据库唯一键限制每张票仅一条成功核销。其他重复扫描返回已使用，并另写失败日志。

无法识别的票可ticket_id=NULL记INVALID；能识别到其他影院票时，为遵守日志票据与当前影院复合外键，当前影院日志不绑定该外院ticket_id，记录WRONG_CINEMA和呈现凭证摘要。不得把外院完整票据资料返回扫码人员。

## 会员、领券、活动与互动

积分账户更新和流水插入在同一事务内，按member_account行锁串行化；points_delta可正可负但balance不能负。支付积分事件使用业务幂等键，退款按原发放比例追回，积分已被消费不足时先按现有可用积分扣减，剩余差额写审核说明并由明确的运营规则处理，不允许悄悄把余额写负。当前课题未要求积分兑换商品，初始实现可先只支持积分累计与按退款追回。

领券先锁券模板，再按template_id+user_id检查领取数、总量和单人限额，插入user_coupon后递增issued_quantity。全部领券和活动奖励须走同一个服务，防止活动发券绕过限额。锁住模板行可以序列化同模板并发领取，唯一coupon_no提供实例幂等保障。券一旦用于支付即USED；订单取消可释放RESERVED券，成功支付后的部分退票不退券，全部退款也默认不自动返券，若运营修改政策必须显式新增补偿记录。

报名先锁活动行，检查报名期、状态和剩余名额，activity_participation唯一键防重复；取消时同事务调整人数。奖励券通过可重试Outbox任务和稳定业务幂等键发放，已发奖励券通过reward_user_coupon_id追踪。

评价先验证本人有效票和允许评价时间，再执行敏感词检测，评价默认PENDING，只有APPROVED进入公开列表与评分视图。后台回复、公告正文做HTML清理；敏感词规则配置限制正则复杂度与执行时长。反馈正文仅提交人、本院授权员工或平台获授权人员可见，is_internal回复不得下发普通用户。

## Redis键建议与一致性

| 键 | 用途 | 初始建议TTL |
|---|---|---|
| film:detail:{filmId} | 影片详情缓存 | 15分钟，加小幅随机抖动 |
| screening:list:{cinemaId}:{filmId}:{date} | 场次列表 | 60秒，加抖动 |
| screening:seats:{screeningId} | 座位图展示缓存 | 2到5秒；购票时仍读数据库 |
| booking:screening:{screeningId} | 短时协调锁 | 3到5秒，不能替代事务 |
| auth:permissions:{userId} | 有效权限缓存 | 5分钟；授权变化主动删除 |
| ticket:nonce:{hash} | 动态码短时加速查询 | 不超过凭证剩余有效期 |
| rate:login:{accountHash} | 登录频率限制 | 按实现配置短窗口 |

业务10分钟锁座和Redis数秒协调锁是不同对象。Redis锁用SET key randomToken NX PX ttl获取；释放用Lua原子比较持有者再删除，不能无条件DEL，以免误删过期后其他请求取得的锁。实现细节参考[Redis官方分布式锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)。本设计依靠MySQL事务保证库存，Redis锁失效、重启或租约过期不应造成超卖。

更新MySQL后由同一事务写Outbox，提交后消费者失效缓存。消费者通过租约认领消息，失败退避重试；PROCESSING且locked_until过期可被回收，消费者本身必须幂等。缓存采用读穿旁路方式，短TTL限制陈旧；排片修改后主动删列表和详情，读路径必要时对版本做校验。当前不引入额外消息中间件，定时轮询Outbox即可支撑毕业设计。

## 票房和统计口径

订单认领的paid_amount为营业收款，重复支付和迟到支付的退款不作为退票额重复扣减营业额。票房净额=已认领支付-对应成功退款；费用如需独立作为手续费收入，另在报表展示，不改变退款流水事实。自然日收入按订单paid_at，退款按渠道succeeded_at归属当日，故当日净额可能为负。

场次上座率=当前SOLD座位数/非DISABLED场次库存数；核销人数另按VERIFIED票计数，不能混为同一指标。统计时排除CANCELLED场次。历史日表中的上座率相关分母和分子均取该日开场的有效场次，不以“该日下单数量”代替。

DAU按事件occurred_at与user_id去重，平台统计不直接相加影院DAU；后台管理人员活动不写普通用户活跃事件。stat_*_daily由定时任务幂等重算，更新calculated_at，清楚标注统计截止时间。实时视图不构成资金对账报告。

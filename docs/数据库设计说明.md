# 数据库设计说明

## 设计范围与架构选择

推荐采用三端共用的模块化单体后端：Uni-app移动端与Vue 3管理端调用同一Spring Boot REST API，MyBatis-Plus访问MySQL 8.0，Redis提供缓存、短时协调和令牌加速验证。两个管理角色可共用一个admin-web工程，通过路由与权限呈现各自工作台。数据库仍分别识别影院范围与平台范围，不能仅靠前端隐藏菜单隔离数据。

可选方案包括：三个完全独立前端工程，界面可独立演进但重复维护较多；按票务、会员、管理拆微服务，部署和分布式事务成本显著增加。对本毕业设计，推荐一个移动端工程、一个含两类后台入口的Web工程、一个按业务模块拆包的后端工程。

当前任务交付数据库结构及设计文档，不包含三端业务实现、真实支付接入或上线部署。工程目录中的README明确了后续代码归属。

## 通用约定

1. 共55张表、4个统计视图。表名和字段使用snake_case，Java属性采用camelCase。
2. 主键为BIGINT自增，外键使用同类型；Java用Long。前端JSON主键以字符串返回，避免JavaScript大整数精度丢失。
3. 金额用DECIMAL(10,2)，单位人民币元；Java用BigDecimal，禁止float/double参与结算。退票与改签按订单明细分摊优惠，最后一张票承担分币舍入差，明细合计必须等于订单金额。
4. 时间使用DATETIME(3)，统一按北京时间写入和解释，数据库会话SET time_zone='+08:00'；JDBC/JVM/定时任务须采用Asia/Shanghai。SQL中的NOW与CURRENT_DATE依赖会话时区。
5. NULL表示缺省值，不以空字符串冒充未知手机号、微信标识或渠道交易号。外部标识和令牌摘要使用区分大小写的排序规则。
6. 所有表均有created_at、updated_at；交易表、票务表、审核和审计记录保留历史，不使用级联删除。账户注销改状态并按需要脱敏，已被引用的影院、影片、影厅与座位停用而不硬删。
7. 状态使用VARCHAR配合CHECK，便于答辩说明和Java枚举映射。CHECK只约束同一行，跨表金额合计、状态联动和权限判断由事务服务负责。
8. schema-model.json用于设计模型与字段字典核对；01_schema.sql是数据库执行入口。后续版本以数据库迁移记录为准，不能靠重复执行初始脚本升级。

## 核心关系

影院1:N影厅，影厅1:N物理座位；影片M:N分类、影片M:N影院；影院片库1:N场次。场次1:N场次座位库存，同一物理座位在不同场次有独立库存。

用户1:N锁座批次，锁座批次1:N锁座明细，锁座批次1:0..1订单；订单1:N订单明细，订单明细1:0..1电子票。订单1:N支付尝试，只认领其中一笔成功支付。退款流水回指真实原支付。

订单1:N退改申请，退改申请1:N退改明细。改签创建新订单，申请同时关联原订单、目标场次和新订单；不覆盖原订单。当前设计限制同一影院内改签，每个申请可包含原订单中部分未核销票。

用户1:0..1平台会员账户，用户M:N影院会员关系；会员账户1:N积分流水；券模板1:N用户券，用户券1:N历史占用但至多一笔有效占用。活动M:N用户。

用户M:N角色，授权可限定某家影院；角色M:N权限。影院入驻与影院管理员账号申请分别审核，审核通过后才激活影院或授予影院角色。

## 重要设计取舍

- 全局影片由系统管理员维护；影院管理员维护cinema_film本院片库、补充说明与排片，不能擅自修改全平台影片。
- 收藏与影片分类用关联表，禁止逗号拼接ID；海报URL、演员数组及资质附件键等非关联展示元数据可用字符串或JSON。
- 平台会员等级和积分归平台，本院会员通过cinema_member保存归属关系。本院消费和观影次数是可重建的派生数据。
- 评价要求存在本人的购票明细，服务层还须验证已核销或场次已结束且票有效。影院管理员可回复、隐藏本院违规内容；平台控制最终安全审核，隐藏与审核均留痕。
- 动态二维码保存短时nonce摘要、有效期和电子票版本，不把固定二维码字符串当作永久入场凭证。随机原值、签名密钥、支付密钥、微信session_key都不存业务表或日志。
- 审计日志、内容审核和Outbox采用资源类型加业务ID的多态引用，故意不设置跨多个资源表的外键；业务服务检查目标存在并保留资源信息。
- 统计表属于缓存式汇总，可以从交易与活动事实重算。全平台活跃用户按user_id去重，不能相加各影院DAU。统计视图仅覆盖已登录用户，匿名访客不计入DAU。

## 数据库已约束与应用仍须约束

数据库约束：场次座位唯一、影厅/座位/场次影院归属一致、有效订单明细库存唯一、锁座库存字段组合合法、支付与退款外部单号幂等、同券不同时占用、同票不并发退改、同票仅一次成功核销、订单内金额非负且算式一致。

应用约束：接口访问权限与影院过滤、影厅场次时间冲突、已存在场次的布局变更限制、锁座时间和状态合法转换、订单和明细合计、回调验签与金额核对、原支付累计退款上限、退改状态联动、会员折扣和优惠券适用范围、活动奖励发放、统计重算及缓存失效。

数据库不会因存在外键就自动阻止越权SELECT，也不会自动执行支付、定时释放座位或刷新二维码。以上业务必须在后续Spring Boot服务层实现并做集成测试。

## 查询与索引

影片列表：先按film.publish_status和release_status过滤，通过film_category_rel按分类筛选；按区县时关联cinema及未来ON_SALE场次，排序使用heat_score或release_date。标题模糊检索在毕业设计数据量下用LIKE，不能声称普通B-tree优化了前置百分号检索。

场次查询：film_id/status/starts_at与cinema_id/status/starts_at索引。用户订单：user_id/created_at。管理员订单：cinema_id/status/created_at。超时任务：seat_hold(status,expires_at)、screening_seat(status,locked_until)、ticket_order(status,expires_at)。

大量历史记录用时间条件和主键游标分页，避免无限深OFFSET。统计用先聚合后关联或相关子查询，避免订单明细、支付、退款多表直接JOIN造成金额倍增。
